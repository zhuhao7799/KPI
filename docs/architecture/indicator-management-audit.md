# 指标体系管理架构与实现审计

审计日期：2026-10-20  
审计范围：`docs/architecture/indicator-management-design.md`、`frontend/src/views/performance/indicators`、`frontend/src/api/kpi`、`backend/kpi-domain`、`backend/kpi-infrastructure-jdbc`、`backend/kpi-ruoyi-adapter`。

## 一、审计结论

当前实现不满足详细设计，不能进入正式验收。主要原因不是单个按钮或样式问题，而是领域模型、接口契约、状态规则和页面实现仍然不一致。

当前状态：**设计需修订，实现需重构，暂不建议继续追加页面补丁。**

## 二、阻断问题

### P0-1：指标体系对象尚未实现

设计定义了“指标体系”对象、体系列表和体系接口，但代码实际只有 `indicator_version`，没有指标体系表、后端接口或前端页面。

影响：无法表达一个体系下多个版本，版本编码的作用域也没有明确归属。

整改：先建立 `indicator_system`，为 `indicator_version` 增加 `system_id`，再调整列表、创建、复制和引用接口。

### P0-2：状态规则互相矛盾

设计同时出现“已发布只读”“已引用允许修改”“已归档仍可编辑”等互相冲突的规则。实现中后端 `saveDraft` 仍禁止 `PUBLISHED` 版本更新，前端又按草稿状态控制操作。

影响：用户无法知道什么情况下能修改，前后端会出现 409 或隐藏按钮不一致。

整改：确定唯一规则。建议采用“发布快照不可原地修改；需要变更时复制为新草稿”的安全模型，或者明确采用“原地修改+影响确认”，二者必须选定一个，不能并存。

### P0-3：发布和删除错误没有稳定业务码

后端仍可能返回 `cannot delete indicator draft`、`cannot publish indicator draft`，没有按设计区分引用、锁定、状态和数据校验错误。

影响：前端无法给出可执行提示，问题只能依靠数据库异常排查。

整改：统一异常映射为 `KPI_VERSION_REFERENCED`、`KPI_VERSION_LOCKED`、`KPI_VERSION_IMMUTABLE` 等业务码，并保留详细原因。

### P0-4：导入不是事务化预览流程

前端使用 `line.split(',')` 解析 CSV，不支持字段内逗号、换行、引号转义，也没有错误行预览。导入后直接调用整版保存接口。

影响：合法 Excel 文件可能解析错误；错误数据可能覆盖整版明细；不符合“预览后确认、失败不落库”的设计。

整改：后端提供导入预校验接口，返回行级错误和临时批次号；用户确认后在一个事务内替换明细。

## 三、重大实现偏差

### P1-1：接口设计与实际接口不一致

设计要求体系级接口和明细级增删改接口，实际主要使用 `POST /indicator-versions/draft` 整体替换明细。前端的单指标编辑页面也通过整版保存实现。

影响：并发编辑容易覆盖他人修改，无法精确审计单条指标变化。

整改：补齐版本明细独立接口，使用版本号或更新时间进行乐观锁校验。

### P1-2：前端仍保留两套编辑模型

版本编辑弹窗、单指标编辑路由和明细行操作同时存在；部分操作编辑 `form.indicators`，部分操作编辑 `version.indicators`，数据源不统一。

影响：页面看似保存成功，但列表、明细和编辑页面可能显示不同数据。

整改：以路由页面为唯一编辑入口，列表只负责展示和跳转；删除、排序、导入都通过明确 API 完成后重新加载。

### P1-3：删除引用检查不完整且依赖数据库表名

删除逻辑检查绩效方案、考核周期和填报记录，但引用定义没有统一引用表；此前已经出现错误表名导致删除返回 409 的问题。

整改：建立统一引用查询服务或 `kpi_indicator_reference` 投影表，所有删除、修改、归档都调用同一套检查。

### P1-4：权重规则尚未真正抽象到评分公式

前端虽已去除 100% 强校验，评分公式仍主要是字符串 `weighted-score-v1`，没有公式注册表、参数定义或后端策略实现。

影响：权重规则仍然散落在前端、领域对象和评分代码中，未来新增公式会继续产生分歧。

整改：建立评分公式注册表和策略接口，统一定义是否需要权重合计、取值范围和计算方式。

### P1-5：空指标草稿规则未完成全链路验证

设计允许创建空草稿，但发布要求至少一条指标。当前前后端已做局部修改，尚未完成接口、列表、发布和删除的完整验证。

整改：增加空草稿、首次新增指标、空草稿删除、空草稿发布失败四个验收用例。

## 四、前端审计

- 页面没有完全按标准单表模板拆分筛选卡片和列表卡片。
- 版本列表、版本明细和指标编辑页面的操作入口仍有重复。
- 导入、导出、下载模板在不同页面出现，入口不一致。
- 大量模板和脚本写在单行，维护和代码审查成本高。
- 当前没有可执行的页面级验收测试。

## 五、后端与数据审计

- 核心表名仍以 `indicator_version`、`indicator_item_snapshot` 为主，与设计中的体系表和引用表不一致。
- 删除明细、保存整版、发布和删除版本的事务边界需要统一审查。
- 审计记录已有调用痕迹，但未确认覆盖修改前后明细、导入批次和引用影响。
- 版本更新缺少并发控制，存在后保存覆盖先保存的问题。
- Maven 执行过程中产生了未跟踪的 `-pl` 和多个 `.flattened-pom.xml` 文件，应清理并加入构建产物排除规则。

## 六、项目管理审计

当前不应继续以“改一个按钮、补一个判断”的方式推进。建议建立以下交付门槛：

1. 设计评审通过后冻结接口和状态规则。
2. 数据库迁移和后端接口先完成并通过接口测试。
3. 前端按单表模板重做三个页面：体系列表、版本列表、版本明细。
4. 完成新增、编辑、删除、发布、引用、导入、导出全流程验收。
5. 通过验收后再进行视觉细节优化。

## 七、建议的整改顺序

### 第一阶段：规则冻结

确定版本是否允许发布后原地修改；确定权重规则归属；确定删除和引用策略；修订本设计中的冲突描述。

### 第二阶段：领域和数据库

补齐指标体系表、版本归属、引用投影、审计明细和乐观锁字段。

### 第三阶段：后端接口

实现稳定错误码、版本明细独立 CRUD、导入预校验、引用检查和一致性校验。

### 第四阶段：前端页面

严格按系统单表模板实现体系列表、版本列表、版本明细；一个指标一个编辑页面；所有操作完成后重新请求服务端数据。

### 第五阶段：验收和交付

执行设计文档中的 11 项验收，并补充并发修改、重复导入、引用后修改、空草稿和权限越权测试。

## 八、审计结论

当前版本适合作为原型验证，不适合作为正式业务模块交付。下一步应先解决 P0 项并修订设计冲突，再开始重构实现；在 P0 项完成前，不应继续增加新的页面按钮或局部交互。
