# 指标体系管理改造方案与计划

## 1. 改造目标

将当前“指标版本列表 + 简单指标表格”改造成适用于高校二级学院和职能部门的指标体系管理模块，支持指标分类、指标属性、版本维护、引用追踪和年度迭代，并保证已经用于考核的历史数据不可被修改。

核心原则：

1. 指标库负责长期维护，指标版本负责年度快照。
2. 草稿版本可以增删改，已发布版本只读。
3. 绩效方案只能选择已发布指标版本。
4. 已被锁定考核周期引用的版本禁止变更和删除。
5. 所有发布、复制、删除和变更动作写入审计记录。

## 2. 当前问题

当前页面存在以下问题：

- 只能查看指标编码、名称、权重和满分。
- 没有指标分类、指标性质、计量单位、评分方向等属性。
- 指标版本和指标库概念没有分开。
- 新增指标依赖整版本提交，无法在目录中单独维护。
- 缺少版本复制、版本对比和引用关系展示。
- 方案、周期与指标版本之间缺少完整的联动校验。
- 已发布版本虽然只读，但页面没有充分解释原因和引用范围。

## 3. 目标业务模型

```text
指标库
  └─ 指标版本（年度快照）
       └─ 绩效方案（组织类别 + 权重 + 评分规则）
            └─ 考核周期（年度或专项周期）
                 └─ 填报、审核、评分、结果
```

### 3.1 指标库

指标库保存长期可复用的指标定义，允许维护指标名称、分类、数据口径和责任部门。

### 3.2 指标版本

指标版本是某一年度或专项考核使用的不可变快照，例如 `2026-v1`、`2027-v1`。版本发布后，不再直接修改原记录。

### 3.3 绩效方案

绩效方案从已发布指标版本中选择指标，并配置组织类别、方案权重和评分规则。二级学院和职能部门可以使用不同方案。

### 3.4 考核周期

考核周期绑定已发布绩效方案，进入锁定状态后，方案和指标版本关系不可变更。

## 4. 指标属性设计

指标明细至少包含以下属性：

| 属性 | 说明 | 示例 |
|---|---|---|
| 指标编码 | 版本内唯一 | TEACH-001 |
| 指标名称 | 展示名称 | 本科教学质量 |
| 指标分类 | 业务分类 | 教学建设 |
| 指标性质 | 定量、定性、加分、扣分、否决 | 定量 |
| 适用组织 | 学院、职能部门或全校 | 二级学院 |
| 计量单位 | 指标的度量单位 | 分、%、项、万元 |
| 指标方向 | 越高越好、越低越好、区间最优 | 越高越好 |
| 评分方式 | 加权、区间、等级、人工评价 | 加权评分 |
| 权重 | 在版本中的权重 | 20% |
| 满分 | 原始分上限 | 100 |
| 数据来源 | 系统取数或人工填报 | 教务系统 |
| 材料要求 | 必须、可选、不需要 | 必须上传 |
| 责任部门 | 指标维护责任单位 | 教务处 |
| 指标说明 | 计算口径和备注 | 计算说明 |

“组织类别”和“指标业务分类”必须分开：前者决定适用对象，后者用于指标目录分类和统计分析。

## 5. 页面方案

### 5.1 指标体系首页

页面采用成熟后台管理系统的“版本列表 + 指标目录”模式：

- 顶部：版本选择、状态筛选、分类筛选、关键词搜索。
- 左侧：指标版本树，显示草稿、已发布、已归档。
- 中间：指标目录表格，支持分页、排序和批量选择。
- 右侧：指标详情抽屉，展示完整属性和引用关系。
- 顶部操作：新建版本、复制版本、发布、归档、版本对比。

### 5.2 草稿版本操作

草稿版本允许：

- 新增指标。
- 编辑指标属性。
- 删除指标。
- 调整指标顺序。
- 批量导入和导出。
- 校验权重和必填项。
- 保存草稿。
- 提交发布。

### 5.3 已发布版本操作

已发布版本只允许：

- 查看指标目录。
- 查看引用方案和考核周期。
- 复制为新版本。
- 查看版本差异。

不提供直接编辑和删除按钮。

## 6. 数据库改造计划

### V11 指标属性扩展

为 `indicator_item_snapshot` 增加：

- `indicator_category`
- `indicator_type`
- `measurement_unit`
- `scoring_method`
- `evidence_required`
- `description`

历史数据使用兼容默认值，确保旧版本可以正常读取和评分。

### 后续数据表

如指标库与版本快照进一步分离，再增加：

- `indicator_catalog`
- `indicator_catalog_category`
- `indicator_version_change_log`
- `indicator_version_reference`

本阶段先扩展现有快照表，避免一次性引入过多表结构。

## 7. 接口计划

```text
GET    /kpi/indicator-versions
GET    /kpi/indicator-versions/{version}
POST   /kpi/indicator-versions/draft
POST   /kpi/indicator-versions/{version}/clone
POST   /kpi/indicator-versions/{version}/publish
DELETE /kpi/indicator-versions/{version}/draft
GET    /kpi/indicator-versions/{version}/references

POST   /kpi/indicator-versions/{version}/items
PUT    /kpi/indicator-versions/{version}/items/{code}
DELETE /kpi/indicator-versions/{version}/items/{code}
PUT    /kpi/indicator-versions/{version}/items/order
```

所有写接口必须校验版本状态、用户权限、引用关系和字段合法性。

## 8. 权限设计

沿用 RuoYi 权限体系，增加或细化以下权限：

| 权限 | 作用 |
|---|---|
| `kpi:indicator:list` | 查看指标版本和目录 |
| `kpi:indicator:add` | 新建指标版本或指标 |
| `kpi:indicator:edit` | 编辑草稿指标 |
| `kpi:indicator:remove` | 删除草稿指标 |
| `kpi:indicator:clone` | 复制已发布版本 |
| `kpi:indicator:publish` | 发布指标版本 |
| `kpi:indicator:reference` | 查看引用关系 |

已发布版本的只读限制必须由后端强制执行，不能只依赖前端隐藏按钮。

## 9. 分阶段开发计划

### 阶段一：模型和迁移

- 增加指标分类和属性字段。
- 为历史指标补充默认值。
- 扩展指标 DTO 和版本快照读取接口。
- 完成迁移脚本和回滚说明。

### 阶段二：指标版本管理

- 新建草稿版本。
- 复制已发布版本。
- 编辑和删除草稿。
- 发布和归档版本。
- 增加版本状态和引用关系展示。

### 阶段三：指标目录管理

- 抽屉式新增和编辑指标。
- 分类、性质、单位、评分方式字典。
- 指标搜索、筛选、排序。
- 权重自动汇总和发布校验。

### 阶段四：方案和周期联动

- 方案只能选择已发布版本。
- 方案指标只能从所选版本中选择。
- 周期只能绑定已发布方案。
- 锁定周期后禁止修改关联版本和方案。

### 阶段五：验收和数据迁移

- 执行历史数据兼容验证。
- 执行学院和职能部门两类方案验证。
- 执行草稿、发布、复制、删除和锁定场景测试。
- 检查权限、日志和异常提示。

## 10. 验收标准

1. 可以新建指标版本草稿。
2. 可以复制已发布版本并生成新草稿。
3. 草稿指标支持增、删、改、查。
4. 指标分类、性质、单位、评分方式可以保存和展示。
5. 指标权重合计不为 100% 时不能发布。
6. 已发布版本不能直接修改或删除。
7. 已引用版本显示引用方案和周期。
8. 被锁定周期引用的版本不能变更。
9. 绩效方案不能选择草稿版本。
10. 周期不能绑定未发布方案或版本不一致的方案。
11. 历史填报和评分结果不受新版本影响。
12. 所有关键操作可在操作日志中追溯。

## 11. 架构评审调整结论

本方案有条件通过。当前阶段先完成“指标版本管理闭环”，暂不同时建设复杂的独立指标库，避免数据模型和迁移范围过大。

调整后的边界如下：

- 第一阶段继续以 `indicator_item_snapshot` 作为指标版本快照。
- 指标版本发布后不可直接修改，只能复制为新版本。
- 指标分类、性质、单位、评分方式、指标方向、材料要求和数据来源使用 RuoYi 字典配置，不在前端写死。
- 已发布版本、已归档版本和锁定周期引用关系必须由后端强制校验。
- 发布、复制、编辑、删除、归档和引用变更必须写入操作日志。
- 独立指标库、自动取数和外部系统对接放到后续阶段。

## 12. 调整后的优先级计划

### P0：指标版本闭环（必须先完成）

1. 增加指标分类和基础属性。
2. 实现草稿版本新增、编辑、删除和查询。
3. 实现已发布版本复制。
4. 实现发布、只读和归档状态控制。
5. 增加编码唯一、必填项、权重 100% 和数值范围校验。
6. 方案只能选择已发布指标版本。
7. 增加指标版本引用关系查询。
8. 增加发布、复制、删除和归档审计日志。

### P1：管理效率和可维护性

1. 指标分类、指标性质、计量单位、评分方式等字典管理。
2. 指标排序和批量调整权重。
3. 版本差异对比。
4. Excel 导入和导出。
5. 引用关系详情和影响范围提示。
6. 方案和考核周期的完整联动校验。

### P2：平台扩展能力

1. 独立指标库和指标复用。
2. 指标变更影响分析。
3. 教务、科研、人事等系统自动取数。
4. 多级指标审核流程。
5. 指标数据质量监控和异常预警。

## 13. 生命周期和权限约束

指标版本统一使用以下状态：

```text
DRAFT      草稿，可增删改
PUBLISHED  已发布，只读，可复制
ARCHIVED   已归档，只读，不允许新方案引用
```

后端必须执行以下规则：

- 已发布版本不能直接编辑或删除。
- 已归档版本不能被新方案引用。
- 被绩效方案引用的草稿版本不能删除。
- 被锁定考核周期引用的版本不能变更。
- 绩效方案必须引用已发布版本。
- 考核周期必须绑定已发布方案，且方案和指标版本必须匹配。

## 14. 评审门槛

进入 P1 前必须完成以下验收：

1. 能够创建草稿版本并维护完整指标属性。
2. 能够复制已发布版本并生成独立草稿。
3. 草稿可以发布，权重不为 100% 时发布失败。
4. 已发布版本无法编辑和删除。
5. 方案和周期只能使用合法的已发布版本。
6. 锁定周期后，版本和方案关系不能变更。
7. 版本引用关系和操作日志可查询。
8. 历史填报、审核和评分结果不受新版本影响。

未达到以上门槛，不进入批量导入、独立指标库和外部系统对接开发。

## 15. 用户代表评审意见

### 15.1 用户认可点

- 年度考核可以通过复制上一版本快速建立新版本。
- 已发布指标不可直接修改，能够保证历史考核结果稳定。
- 二级学院和职能部门可以使用不同绩效方案。
- 方案、指标版本和考核周期之间的关系清晰。
- 发布前有权重和必填项校验，降低配置错误。
- 引用关系可见，管理员能知道修改会影响哪些业务。

### 15.2 用户关注点

- 页面不能只显示编码和权重，必须能看懂指标的业务含义。
- 分类、指标性质、评分方式等字段应使用下拉选项，避免不同人员填写不同名称。
- “发布”操作必须有明确提示，并显示影响范围。
- 已发布版本需要提供“复制为新版本”，不能让用户误以为系统不能修改指标。
- 权重合计、适用组织和材料要求应在页面上实时提示。
- 方案绑定时应只显示可用的已发布方案，不能让用户手工输入编码。
- 锁定周期后，页面需要明确显示锁定原因和不可修改范围。

### 15.3 用户验收场景

1. 管理员复制 `2026-v1` 为 `2027-v1`。
2. 在草稿中新增“本科教学质量”指标并设置分类、性质、单位和评分方式。
3. 删除一个不再使用的草稿指标。
4. 调整指标权重，系统实时显示权重合计。
5. 权重不为 100% 时尝试发布，系统阻止并提示差额。
6. 权重为 100% 后发布，版本变为只读。
7. 进入绩效方案，只能选择 `2027-v1` 等已发布版本。
8. 进入考核周期，只能绑定已发布且匹配的绩效方案。
9. 锁定周期后尝试修改版本，系统阻止并说明引用关系。
10. 查看版本引用，能看到具体方案和考核周期。

### 15.4 用户评审结论

方案符合高校年度绩效考核的实际操作习惯，用户侧同意进入 P0 开发。P0 验收必须以完整业务场景验证为准，不能只验证接口返回成功。
